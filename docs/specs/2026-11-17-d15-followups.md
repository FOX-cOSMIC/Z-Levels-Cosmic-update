# Spec: D15 follow-ups (tracker filing, reservation restore, floor loops, haul count)

Date: 2026-11-17. Branch `fix/d15-followups`, from `zlevels-1.7` at `91ef5fd`. Lucas asked on 2026-11-17 to finish the project and merge without asking. These are the four roadmap items D15 left open (`docs/roadmap.md`, "Reachability bugs").

## Goal

1. **Filing closes when a search ends.** `ResetJobTrackerFor` opens filing: it sets `LocalTargetInfo_Constructor_Patch.curPawnJobTracker`, and from then on every `new LocalTargetInfo(cell)`, built by any pawn or any code, is filed into that colonist's tracker under `ZUtils.currentLookedIntoMap`. `BuildJobListFor` closes it after a search that finds a job. A search that finds nothing, a search that throws, and a reset with no search after it leave it open.
2. **The reservation patches move the colonist back after a throw.** `ReservationManager_CanReserve_Patch` and `ReservationManager_CanReserveStack_Patch` move the colonist to the target's floor, keep the old floor in static fields, and move it back in a postfix. Harmony skips the postfix when the call throws.
3. **The bill, refuel and forced float-menu loops set the floor field.** They move the colonist (and the bench or the fuel target) to each floor and never set `ZUtils.currentLookedIntoMap`, so a cell built in the loop is filed under the colonist's own floor while the colonist looks into another.
4. **Proof of the haul count on another floor.** `HaulToCellStorageJob` reads the storage on `storeMap` since D15 round 2. No row checks the job count.

## Decisions

- Filing is closed at the end of the searches, not at each reset. `ResetJobTrackerFor` keeps opening it, because about 30 callers reset and then search. Three places close it:
  - The work-search prefix (`JobPatches.TryIssueJobPackagePatch`), after its full search, whether the search found a job, found nothing, or threw.
  - A finalizer on `Pawn_JobTracker.DetermineNextJob`, which covers every think-tree search (food, joy, rest, combat, the work search) and the resets inside them.
  - A finalizer on the float-menu patch (`FloatMenuMakerMap.GetOptions`), which covers the right-click searches.
  Closing removes no filed cells: `CanReach_Patch` still reads the entries the search made. A cell built after the search is no longer filed. Since D15 the field is the own floor after a search, so such a cell was filed under the own floor, which gives the same answer as no entry, except that it overwrote an entry the search had made under another floor. Closing removes that overwrite.
- The reservation patches keep the colonist's floor and cell in Harmony's `__state`, and move it back in a finalizer, as `CanReach_Patch` does since D15. The `CanReserve` postfix keeps its reservation-conflict check, which reads no floor of the claimant. The finalizer runs after it.
- A new `ZUtils.LookingInto(maps, ownFloor)` iterator sets the field to each floor before yielding it, and puts it back on `ownFloor` when the enumeration ends, stops early or throws, as the D15 iterators do. The bill, refuel and float-menu loops wrap their floor lists in it. `ownFloor` is the colonist's floor before the loop.
- The haul count gets a proof row only. Its fix is already merged (D15, round 2), so the row has no red run on this branch.

## Out of scope

- The other reset sites outside the think tree and the float menu: the stair arrival check (`Toils_ZLevels.cs:67`), which ends the job and so runs `DetermineNextJob` next; and the call-colonists targeter (`UI/CallColonistsTargeter.cs`), which is a user order that builds its own goto cell. Their filing closes at the colonist's next think-tree search.
- A row for the float-menu loop. Building the right-click menu in a validation run needs a UI click context. The loop uses the same helper as the bill and refuel loops.
- Cross-level storage reachability (its own plan).

## Acceptance checks

The new scenario switch is `-D15Followups`. Its required pass line is `d15 follow-ups`.

1. Before the fix, the scenario fails at least these rows: the empty work search leaves filing open; the `DetermineNextJob` row; both `CanReserve` throw rows; the `CanReserveStack` throw row; the bill row; the refuel row. Run on the scenario commit with the product code of `91ef5fd`, and observe `FAIL` on each.
2. After the fix, `tools/Invoke-RuntimeValidation.ps1 -D15Followups` prints `Runtime validation passed. Evidence: <run folder>`.
3. Filing rows: after a work search that finds nothing (`JobGiver_Work.TryIssueJobPackage` through the Z-Levels prefix, all work off), `curPawnJobTracker` is null, and a cell built afterwards is not in the colonist's tracker. After a reset followed by `Pawn_JobTracker.DetermineNextJob`, `curPawnJobTracker` is null.
4. Reservation rows: a harness prefix throws inside `ReservationManager.CanReserve` while the colonist stands on the lower floor. For a thing on the lower floor and for a cell filed under the lower floor, the exception reaches the caller and the colonist is back on its own floor and cell. The same for `CanReserveStack` with a thing on the lower floor. A normal `CanReserve` of a thing on the lower floor also leaves the colonist on its own floor and cell.
5. Floor-loop rows: a harness prefix on `WorkGiver_DoBill.TryFindBestBillIngredients` (bill loop) and one on `WorkGiver_Refuel.HasJobOnThing` (refuel loop) record the colonist's floor and the field on each call. Each loop must reach the lower floor, the field must equal the colonist's floor on every call, and the field must be the own floor after the loop.
6. Haul-count row: a one-cell stockpile on the lower floor holds 50 steel. `HaulToCellStorageJob` for 60 surface steel to that cell, with `storeMap` the lower floor and `fitInStoreCell` true, gives a job count of 25.
7. `-FloorStateAfterSearch` and `-SearchThrowState` still pass.
8. The full regression (core, every scenario switch, and RimatomicsPlusPlus) runs on the fix commit with a clean tree. Every run passes except `-CoolingNoColumns`, which fails by design. Every run builds the same `ZLevels.dll` hash.
9. `tools/Check-Docs.ps1` passes.
