# Vault v1 implementation plan

Date: 2026-10-30
Spec: `docs/superpowers/specs/2026-10-29-vault-pocket-dimension.md` (acceptance a to h).
Status: draft. Re-read and corrected before any code is written.

## Scope

- One vault entrance type, placeable on the surface only.
- One shared pocket map for all vault entrances. Each entrance has its own exit inside it.
- Colonists enter, build inside, and leave. Items on the load list are hauled in and dropped on the pocket floor next to the exit.
- Storage is a stockpile zone inside the pocket.
- Not in v1: power, tubes, raids on pocket maps, existing saves.

Chosen in this plan, to redirect if wrong:
- Several entrances are in scope (acceptance b). Each costs one exit.
- The player places the storage zone (the spec's open item; recommended).

## Engine facts (checked in the 1.7 DLL and the decompiles in `.artifacts/ilspy/`)

- `MapPortal.GetOtherMap()` calls `GeneratePocketMap()` when `PocketMap` is null. That calls `protected virtual Map GeneratePocketMapInt()`. A subclass can override it and return the shared pocket.
- `PocketMapExit.SpawnSetup` links to `PocketMapUtility.currentlyGeneratingPortal` (public static, `MapPortal`) when not respawning, and sets `entrance.exit = this`. Each exit therefore needs that field set before it spawns.
- `PortalContainerProxy.TryAdd` drops each item on `GetOtherMap()` at `GetDestinationLocation()`, which is the exit position. Items do not stay in a container.
- `MapPortal.AddToTheToLoadList` is the load-list API that `Dialog_EnterPortal` calls (the enter gizmo). `JobDriver_HaulToPortal` takes its items from that list.
- `MapPortal.ExposeData` saves `pocketMap`, `exit`, `beenEntered` and `leftToLoad`.
- The vanilla exit to model on is the `CaveExit` ThingDef (`Data/Core/Defs/ThingDefs_Buildings/Buildings_Misc.xml`, ParentName `PocketMapExit`).
- `ZUtils.GetMapComponentZLevel` and `ZLevelsManager.GetZIndexFor` fail on pocket maps (no component). Every mod patch must check `IsPocketMap` first.

## Tasks

Each task: write a red validation (a runner flag, like `-InfestationGuard`), watch it fail, change the code, watch it pass, commit. Validation runs take a few minutes each.

### Task 1: Entrance def, class, and surface-only placement

Files: `ZLevels/Source/ZLevels/ZLevels/Vault/Building_VaultEntrance.cs`, `ZLevels/Source/ZLevels/ZLevels/Vault/PlaceWorker_VaultSurface.cs`, `ZLevels/Common/Defs/Buildings/Vault.xml`.

1. Red: runner flag `-Vault`. Stage 1 asks `GenConstruct.CanPlaceBlueprintAt` for the entrance def on a surface cell and on a lower cell. Before the def exists, the stage fails.
2. Add the def: `ParentName` `BuildingBase`, `thingClass` `Building_VaultEntrance`, `placeWorkers` `PlaceWorker_VaultSurface`, and a `portal` block (`MapPortalProperties`) with `pocketMapGenerator` `ZL_VaultPocket` and `exitDef` `ZL_VaultExit`.
3. Green: the lower cell is refused, and the surface cell is accepted.
4. Check that the `portal` block loads. A bad def shows as an error in `Player.log`.

### Task 2: Shared pocket and per-entrance exits

Files: `Vault/Building_VaultEntrance.cs` (override `GeneratePocketMapInt`), `Vault/VaultPocket.cs` (a `GameComponent` that holds the pocket map and saves it, so later entrances find it), `Common/Defs/MapGenerator/VaultPocket.xml` (flat floor, no rock).

1. Red: stage 2 places one entrance on the surface and calls `GetOtherMap()`. It expects a pocket map where `IsPocketMap` is true. Before the code exists, the stage fails.
2. Green: the first entrance creates the pocket, and the pocket is not registered in `ZLevelsManager`.
3. Second entrance: stage 2b places another surface entrance. Its `GetOtherMap()` returns the same pocket, and its `exit.entrance` is that second entrance. The subclass spawns that exit itself, after it sets `PocketMapUtility.currentlyGeneratingPortal` to its own entrance.
4. Check `destroyOnParentMapAbandoned`. The spec's risk says the default is true. Set it to false on the pocket generator's properties, or document why not.

### Task 3: Enter, build inside, exit (acceptance c)

1. Red: stage 3 makes a colonist enter through the entrance, places a wall blueprint inside the pocket, waits for the build, and waits for the colonist to leave through the exit.
2. Expected first failures: mod patches that assume a `MapComponentZLevel` on every map. Fix each one with an `IsPocketMap` check first, one patch at a time, with a red run for each.
3. Green: the wall stands, and the colonist is back on the surface.

### Task 4: Load list and hauling (acceptance d)

1. Red: stage 4 puts seven wood logs on the surface, calls `AddToTheToLoadList` on an entrance with a `TransferableOneWay` that holds those logs, and waits for colonists to haul them in with no forced job. Record the counts on the surface and on the pocket map before and after.
2. Expected first failures: the cross-level hauling code in the mod, when the destination is a pocket map.
3. Green: all seven logs end on the pocket map, near the exit.
4. The storage zone is placed by the test, as the player would place it. The spec's open item covers the default.

### Task 5: Wealth (acceptance e)

1. Red: stage 5 records the surface's wealth with the seven logs on the surface, then after they reach the pocket map. Expected: the total still counts them.
2. Green: the total drops by the logs' value once they are on the pocket map.
3. Check both the mod's wealth patch and the vanilla `PlayerWealthForStoryteller`.

### Task 6: Save and reload (acceptance f)

1. Red: stage 6 saves with a colonist inside the pocket, a wall built there, and logs on the pocket floor. It reloads and checks that the pocket exists, the colonist is on the pocket map at the saved cell, the wall stands, and the logs are on the pocket floor.
2. Expected first failures: the mod's `ExposeData` or lookups on pocket maps after load, and the per-entrance exit links.
3. Green: all four checks pass after reload.

### Task 7: Infestation on the pocket map (acceptance g)

1. The guard (`IsPocketMap` in the infestation patch) is already in HEAD, so a red run is not possible without removing it. Record that in the report.
2. Stage 7 calls the infestation worker with the pocket map as the target. Expected: no record, no hole.
3. The depth guard's red run is the evidence that the check can fail. This pocket case alone was never red.

### Task 8: Docs, roadmap, and commits

1. Add a vault section to `docs/validation-report.md`. List each run, red and green.
2. Update `docs/levels-and-events.md` with the pocket map facts: no registration, no wealth in the mod's patches, the exit links.

## Risks

- Dropped items need a zone inside the pocket to be stored. Without a zone they lie on the floor near the exit.
- The pocket has no `MapComponentZLevel`. Any mod patch that reads one on a pocket map must check `IsPocketMap` first.
- Overriding `GeneratePocketMapInt` is new code on an engine path. Confirm it works with a second entrance before relying on it.
- The `portal` XML shape is not in the vanilla Core defs. Task 1 step 4 checks it by loading the def.
- The main chain and the stale-map fixes are already in HEAD. Re-run the main chain after each task that touches shared code.
